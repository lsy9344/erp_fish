## 결정 요약

| 항목       | 결정                        | 근거                                                            |
| ---------- | --------------------------- | --------------------------------------------------------------- |
| DB 접근    | **Text-to-SQL 안 쓴다**     | 매출은 컬럼 하나가 아니다. 기존 리포트 함수를 도구로 감싼다.    |
| 도구 개수  | **7개** (질문 축 단위)      | 화면 12개 ≠ 질문 축. 거절 로그 보고 축을 하나씩 추가한다.       |

| 모델 등급  | **소형(mini)**              | 어려운 계산은 기존 코드가 한다. AI는 도구 고르기 + 문장 만들기. |
| 루프 상한  | **3라운드**                 | 원인 도구 하나에 근거가 다 들어 있다. 6은 과했다.               |
| 도구 출력  | **필드 allowlist**          | 개인정보 차단과 토큰 절감이 같은 장치다.                        |

| SQL 폴백   | **안 만든다**               | 만드는 순간 LLM이 쉬운 길로 가고 결정 1이 무너진다.             |
| 적용 범위  | **본사 화면만**             | 지점장 화면은 하단 메뉴와 충돌 + 권한 범위가 다르다.            |
| 미해결     | **외부 전송 승인**          | 고객사 확인 필요. 유일한 차단 항목(§오픈 질문 1).               |

이 결정들은 따로 놀지 않는다. **결정 1이 나머지를 끌고 간다** — 어려운 계산을 기존 코드에 맡겼기 때문에 작은 모델로 충분하고, 그래서 싸고, 그래서 숫자가 리포트 화면과 항상 일치한다.

## 핵심 설계 결정

### 결정 1 — 챗봇은 "리포트 계층의 자연어 프론트엔드"다. Text-to-SQL이 아니다

LLM이 SQL을 생성해 DB에 직접 질의하는 방식은 이 프로젝트에서 **틀린 숫자를 만든다.**

- `매출`은 컬럼 하나가 아니다. `totalSalesAmount + carryoverSalesAmount`이고, 그 위에 `CorrectionRecord` 최신 정정값이 덮인다 (`ledger.ts:785`, `queries.ts:2146`).
- `매출원가`는 FIFO 로트 소진으로 계산되며, 산출 불가한 장부는 합산에서 제외해야 한다(`queries.ts:2047-2052`). 단순 `SUM`은 조용히 틀린다.
- `품목 매출`은 판매계획가 + FIFO 원가 기반 **추정치**이고 `statusLabel`로 신뢰도를 구분한다.
- 챗봇이 대시보드와 다른 숫자를 자신 있게 답하면, 답이 없는 것보다 나쁘다.

그런데 이 계산은 **이미 다 짜여 있다.** `src/features/reports/*`와 `src/features/labor/*`가 정확히 그 일을 하고, 각 함수가 `requireReportAccess()` / `requireLaborViewAccess()` / `getHeadquartersStoreScope()`를 내부에서 호출한다.

따라서: **기존 리포트 함수를 얇게 감싼 도구(tool)를 LLM에 노출한다.** 부수 효과로 권한·지점 범위·민감 권한 게이트가 전부 공짜로 따라온다. 챗봇 코드에 인가 로직을 새로 쓰지 않는다.

### 결정 2 — 도구를 "질문 축(axis)" 단위로 자른다. 리포트 화면 단위가 아니다

리포트 페이지는 12개지만 질문 축은 6개다. 페이지마다 도구를 만들면 LLM이 고르지 못한다. 축으로 자르면 6개로 전 영역이 덮인다. (§도구 카탈로그)

### 결정 3 — 새 런타임 의존성 0개. OpenAI Chat Completions를 `fetch`로 호출한다

SDK 없이 `fetch`(`line-client.ts`와 동형). 채팅창은 기존 `ui/sheet.tsx`. 필요한 건 도구 호출 루프 하나뿐이다.

제공자를 OpenAI로 잡은 이유는 **자동 프롬프트 캐싱**이다. 이 설계는 고정 오버헤드(시스템 프롬프트 + 도구 스키마 ~1,900토큰)를 매 호출 재전송하는데, 고정 블록을 프롬프트 맨 앞에 두면 캐싱이 추가 코드 없이 걸린다. 바꾸더라도 `llm-client.ts` 한 파일 교체다.

### 결정 4 — 소형(mini) 모델로 간다. 비용은 설계로 잡는다

챗봇이 하는 일은 (a) 도구와 인자 고르기 (b) 받은 JSON을 한국어 문장으로 옮기기, 둘뿐이다. **어려운 계산은 전부 기존 리포트 코드가 한다(결정 1).** AI에게 암산을 안 시키므로 큰 모델이 필요 없다.

결정 1이 비용까지 끌고 가는 지점이다. LLM이 직접 계산하는 설계였다면 상위 모델 + 긴 추론이 필요했을 것이다. 상세는 §비용 설계.

### 결정 5 — 스트리밍·대화 영속화 없음

단발 JSON 응답, 히스토리는 클라이언트 상태. → 스킵한 것: 스트리밍(답변이 길어져 체감 지연이 생기면 추가), 대화 저장·챗 감사 로그(챗봇 답변 기반 의사결정 추적이 요구될 때 추가).

## 도구 카탈로그

각 도구는 **인자 정규화 → 기존 함수 호출 → 출력 필드 추리기**만 한다. 계산 로직을 새로 쓰지 않는다.

"출력 필드 추리기"는 장식이 아니다. 리포트 함수는 화면 렌더링용이라 `detailHref`(링크 주소)·`storeId`(cuid) 같은 LLM이 절대 쓰지 않는 값이 대부분이고, 이걸 그대로 넘기면 토큰이 4~40배로 뛴다. **같은 allowlist가 개인정보 차단 장치이기도 하다.** 한 번 만들어 두 문제를 막는다(§비용 설계, §5).

### 1. `get_period_metrics` — 수치의 기본 축

```
목적: 임의 기간·지점의 8대 지표. 전기 대비 증감까지.
입력: startDate, endDate (YYYY-MM-DD)
      storeName?     // 미지정 = 권한 범위 전체 지점
      compareTo?     // "previous" | {baseStartDate, baseEndDate}
구현: getHqPeriodContrastReport  (queries.ts:757)
반환: 지점별 { 매출, 매출이익, 이익률, 평균근무인원, 인당생산성,
              평균재고, 평균매출, 재고비율 } + contrastRows(증감)
```

`12월 매출` → `startDate=2025-12-01, endDate=2025-12-31`. `8월 1일 강서수산 매출` → 하루 범위 + `storeName`. `지난달 대비` → `compareTo="previous"`. **수치를 묻는 질문의 대부분이 이 도구 하나로 끝난다.**

### 2. `get_month_overview` — 원인 분석의 축

```
목적: 한 달의 손익 구조·손실 분해·일별 추이·지점 순위·경보.
입력: month (YYYY-MM), storeName?
구현: getHqReportOverview  (overview.ts:950)
반환: summary(매출/이익/순익/손실)
      profitAndLoss.steps  ← 매출→원가→인건비→고정비→순익 워터폴
      lossBreakdown.items  ← 손실 항목별 금액·비중
      salesTrend           ← 일별 당월 vs 전월
      rankings             ← 지표별 지점 순위 + 제외 사유
      actions              ← severity 붙은 경보
      dataQuality          ← 미마감 건수, 계산 기준 라벨
```

`순익이 줄어든 원인` 같은 질문의 1차 근거다. 워터폴 단계가 곧 기여도이고, `actions`가 곧 이상 신호다.

### 3. `get_product_sales` — 품목 축

```
목적: 기간·지점의 품목별 판매 실적 상위 N.
입력: startDate, endDate, storeName?, metric("quantity"|"amount"), limit(1~20)
구현: getHqProductSalesReportForRange  (queries.ts:1565)
반환: [{ productName, productSpec, productCategory,
         soldQuantity, estimatedSalesAmount, lossQuantity, statusLabel }]
```

`estimatedSalesAmount`는 판매계획가 기반 **추정치**다. 기본 정렬 지표를 `quantity`로 둔 이유 — 수량은 추정이 아니다.

### 4. `get_monthly_pnl` — 비용 세부 축

```
목적: 월별 손익을 비용 항목까지 펼친다.
입력: month (YYYY-MM), storeName?
구현: buildMonthlyProfitAndLoss  (monthly-profit-loss.ts:74)
반환: [{ storeName, salesAmount, cogsAmount, grossProfit, grossMarginRate,
         laborAmount, fixedCosts{항목별}, otherExpenseAmount,
         hqAdjustmentAmount, netAmount, adjustmentReason }]
```

워터폴(도구 2)보다 세밀하다. `고정비 얼마 나갔어`, `본사 조정 왜 잡혔어` 류를 받는다.

### 5. `get_labor_report` — 인건비·급여 축 **(LABOR_VIEW 전용)**

```
목적: 기간·지점·직원별 인건비 실적.
입력: month? | from/to, storeName?, workerName?
구현: getHeadquartersLaborReport  (headquarters-labor-queries.ts:506)
       → 내부에서 requireLaborViewAccess() 수행. 권한 없으면 여기서 차단된다.
반환 allowlist: workerName, storeName, businessDate, workedDayCount,
                dailyWage, laborAmount, 합계
반환 금지:      bankAccount, address, phone, 주민등록 관련 일체
```

`직원 급여` 질문이 여기로 온다. **출력 allowlist는 선택이 아니라 필수다** — `Employee` 모델에 계좌번호·주소·연락처가 있고, 이 값들이 외부 LLM API로 나가면 안 된다. 도구는 `EmployeeListItem`을 그대로 반환하지 않고 명시적으로 나열한 필드만 통과시킨다.

> `src/server/sensitive-fields.ts`의 `omitSensitiveFields`를 여기에 재사용하지 말 것. 그 함수는 **지점장에게 원가·마진을 숨기는** 반대 방향 마스킹이고, 본사 챗봇 사용자는 그 값을 볼 권한이 있다. PII 차단은 별도의 명시적 allowlist로 한다.

### 6. `get_inventory_position` — 재고 축

```
목적: 지점·품목별 재고 수량·금액·장기재고.
입력: date? | startDate/endDate, storeName?
구현: getHqInventoryPositionReport  (inventory-position-queries.ts:282)
```

### 7. `get_loss_breakdown` — 손실 유형 축 (2026-08-10 추가)

```
목적: 기간·지점의 손실을 손실 유형별·품목별로 펼친다(떨이·폐기·파손 등).
입력: startDate, endDate, storeName?, lossTypeNames?(부분 일치 OR), limit(1~20)
구현: getHqLossItemsForRange  (queries.ts, getLedgerProfitSummariesForRange 위임)
반환: 유형별[{유형, 수량, 금액, 건수, 금액미산정건수}]  ← 절단 없음
      품목별상위[{품목, 규격, 유형, 지점, 수량, 금액}]
      기간내존재하는유형, 일치하지않은유형, 합계
```

도구 2의 `lossBreakdown.items`로는 이 질문을 답할 수 없어 축을 하나 더 열었다. 그쪽은 도넛 차트용이라 유형을 **상위 3개 + "기타"로 뭉친다**(`overview.ts:462`). `8월 떨이·폐기 합계`를 물었을 때 유형 이름 자체가 LLM에 보이지 않아 "산출 불가"로 답한 사례가 있었다.

금액은 판매계획가가 등록된 손실만 산정된다(`losses/actions.ts:385-406` — 없으면 0). 그래서 수량·금액을 따로 내보내고 `금액미산정건수`를 함께 실어, 0원을 "손실 없음"으로 오독하지 않게 한다. 유형 이름이 하나도 안 맞으면 `일치하지않은유형`으로 되돌려 0원 대신 되묻게 한다.

### 지점명 매칭 (전 도구 공통)

`Store.name`은 `@unique`(`schema.prisma:120`). 공백 제거 후 부분 일치.

- 1건 매칭 → 채택
- 0건 → 권한 범위 내 지점 목록을 반환해 되묻게 한다
- 2건 이상 → 후보를 반환해 되묻게 한다

**추측 금지.** 엉뚱한 지점 숫자를 자신 있게 답하는 것이 최악의 실패 모드다. 시스템 프롬프트에 접근 가능 지점 목록을 미리 주입해 이 왕복을 대부분 없앤다.

## "원인" 질문 처리 규칙

`순익이 줄어든 원인` 류는 도구 여러 개의 조합이다. 전형적 경로:

```
get_month_overview(해당 월)          → 워터폴에서 어느 단계가 빠졌는지
  └ get_period_metrics(compareTo)    → 전월 대비 어느 지표가 얼마나 변했는지
      └ get_product_sales / get_monthly_pnl  → 품목·비용 항목까지 드릴다운
```

다만 `get_month_overview` 하나에 워터폴·손실 분해·순위·경보가 **모두** 들어 있어, 실제로는 1~2라운드에 끝나는 경우가 대부분이다. 드릴다운까지 3라운드면 충분하다(수치 질문은 1라운드).

프롬프트가 강제할 것:

1. **원인은 숫자 차이로만 뒷받침한다.** "이익률이 25.9% → 24.5%로 1.4%p 낮아졌고 손실이 320만원 늘었습니다" — 도구 결과에 있는 값만 쓴다.
2. **인과 단정 금지.** "~때문입니다"가 아니라 "~가 가장 큰 감소 요인입니다". DB는 상관을 보여줄 뿐 원인을 모른다.
3. **미마감 데이터를 경고한다.** `dataQuality.missingCount > 0`이면 "미마감 N일이 있어 값이 바뀔 수 있습니다"를 붙인다.
4. 계산 불가 항목(`statusLabel: "계산 불가"`, `grossProfit: null`)은 0으로 취급하지 않고 "산출 불가"로 말한다.

## 시스템 프롬프트 규칙

1. **오늘 날짜(KST)와 접근 가능 지점 목록을 주입한다.** `12월`처럼 연도가 없으면 오늘 기준 가장 가까운 과거 12월로 해석하고, 해석 결과를 답변에 명시한다.
2. **도구 결과에 없는 숫자는 절대 말하지 않는다.** 추정·보간·암산 금지.
3. **도구로 답할 수 없으면 거절한다.** "그 질문은 아직 지원하지 않습니다. 매출·손익·품목·인건비·재고 관련해서 물어봐 주세요."
4. 불확실하면 되묻는다(지점 모호, 기간 불명확).
5. `추정`·`부분 합계`·`미마감`은 반드시 한 문장으로 덧붙인다.
6. 금액은 천 단위 구분, 수량·비율은 소수 둘째 자리(`src/lib/format.ts` 표기와 일치).
7. 답변 2~4문장, 평문. 항목이 3개 넘으면 짧은 목록 허용.

## 비용 설계

토큰은 이 기능의 유일한 반복 비용이다. 절감 장치를 나중에 붙이지 않고 처음부터 넣는다.

### 질문 1건당 토큰

| 구성                                          | 토큰       |
| --------------------------------------------- | ---------- |
| 시스템 프롬프트(규칙 + 오늘 날짜 + 지점 목록) | ~700       |
| 도구 스키마 6개                               | ~1,200     |
| **고정 오버헤드 (매 호출 재전송)**            | **~1,900** |

도구 호출은 라운드마다 직전까지의 대화 전체를 다시 보낸다. **라운드 수가 곧 비용이다.**

| 질문 유형            | LLM 호출 | 입력 토큰 | 출력 |
| -------------------- | -------- | --------- | ---- |
| `12월 매출`          | 2회      | ~4,000    | ~150 |
| `7월 많이 팔린 품목` | 2회      | ~4,500    | ~200 |
| `순익이 줄어든 원인` | 3~4회    | ~11,000   | ~400 |

3명 × 하루 20질문 × 월 22일 = 월 1,320질문, 평균 6,100 입력 토큰 → **월 약 800만 입력 토큰**.

### 절감 장치 3개

**1. 도구 결과를 잘라서 넘긴다 (효과 4~40배 — 가장 큼)**

| 도구                 | 원본 그대로            | 다듬은 뒤       | 버리는 것                                  |
| -------------------- | ---------------------- | --------------- | ------------------------------------------ |
| `get_month_overview` | 3,500~5,000            | ~1,000          | `detailHref`, `storeId`(cuid), 중복 요약문 |
| `get_product_sales`  | 최대 12,000 (품목 200) | ~300 (상위 5개) | 상위 N 밖 전량                             |
| `get_labor_report`   | 월 수백 행             | ~500            | 개인정보 필드 + 행 단위 원본               |

`limit`은 LLM이 아니라 **서버가 강제한다.** LLM이 `limit=200`을 넣어도 서버가 20에서 자른다.

**2. 고정 블록을 프롬프트 맨 앞에 둔다 (자동 프롬프트 캐싱)**

시스템 프롬프트 + 도구 스키마(~1,900토큰)는 요청마다 한 글자도 안 바뀐다. 이 블록을 **항상 같은 순서로 맨 앞**에 두면 제공자의 자동 프롬프트 캐싱이 걸린다. 오늘 날짜는 하루 단위로만 바뀌므로 고정 블록에 포함해도 된다. 사용자별로 달라지는 내용을 앞에 섞지 않는 것이 유일한 조건이고, 추가 코드는 없다.

> 캐싱 최소 토큰 임계값과 적용 조건은 제공자 문서로 확인한다. 고정 내용을 앞에 두는 것 자체는 어느 제공자에서도 손해가 없다.

**3. 루프 상한 3라운드** (§"원인" 질문 처리 규칙)

### 모델 등급

**소형(mini) 등급으로 시작한다.** 모델명은 `OPENAI_CHAT_MODEL`로 두어 코드 변경 없이 바꾼다.

원인 분석 답변 품질이 부족하면 **그 경로만** 상위 모델로 올린다(`get_month_overview`를 호출한 요청만 분기). 전체를 올리지 않는다.

> 단가는 제공자 요금표를 확인해 위 토큰 수에 곱한다. 등급 선택이 최종 비용을 두 자릿수 배 좌우하므로, 소형으로 시작해 필요한 경로만 올리는 순서를 지킨다.

## 도구 카탈로그의 경계

6개 도구는 **계산이 필요한 모든 질문**을 덮는다. 덮지 못하는 건 단순 사실 조회의 긴 꼬리다: "지난주 목요일 누가 근무했어", "이 품목 언제부터 취급했어", "미마감 장부 몇 건이야" 같은 것들.

여기에 read-only SQL 폴백을 **v1에서는 두지 않는다.** 이유: SQL로 답할 수 있는 것에는 `매출`·`이익` 컬럼도 포함되고, LLM은 그 쪽이 더 쉬워 보이면 그리로 간다. 그 순간 리포트와 다른 숫자가 나오고, 결정 1의 근거가 통째로 무너진다.

**확장 규칙**: 거절된 질문을 로그로 남기고(질문 원문 + `usedTools: []`), 반복되는 유형이 확인되면 그 유형만 도구로 추가한다. 추측으로 늘리지 않는다.
