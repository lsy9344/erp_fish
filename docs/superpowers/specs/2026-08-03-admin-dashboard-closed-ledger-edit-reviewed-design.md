# 관리자 홈 지표 및 마스터 마감 장부 수정 설계

## 문서 정정 배경

이전 문서는 매입·손실·재고·지출·근무·급여·매출/결제 편집 기능 전체를 신규 구현 대상으로 설명했다.

하지만 해당 업무 항목의 본사 편집 화면과 저장 기능은 이미 존재한다. 이번 작업은 기존 편집 기능을 다시 만드는 작업이 아니다.

실제 변경 범위는 다음 두 가지다.

1. 기존 본사 편집 기능을 `HEADQUARTERS_CLOSED` 상태의 과거 장부에서도 마스터 계정에 한해 사용할 수 있게 한다.
2. 기존 본사 재고 편집에 빠져 있는 `판매한 가격` 수정 기능을 추가한다.

즉, 기존 기능을 재사용하면서 마감 상태와 판매가격 편집의 빈틈만 보완한다.

## 요청 요약

### 관리자 홈

1. `매출 구성`을 다음 세 값으로 단순화한다.
   - `매출`: 이월 매출을 합한 매출
   - `예상매출`: 기존 `분석` 값의 라벨 변경
   - `재고금액`: 선택한 일자의 마감 장부 재고 총액
2. `이월` 금액은 별도 줄로 표시하지 않는다.
3. `실제 / 예상 마진율`은 유지하되 `경보 기준` 문구는 제거한다.

### 마감 장부 수정

1. 본사 마스터 계정은 `HEADQUARTERS_CLOSED` 상태의 과거 장부도 수정할 수 있다.
2. 기존 본사 편집 화면에서 제공하는 모든 업무 항목을 그대로 수정할 수 있다.
3. 지점장이 해당 영업일에 입력한 `판매한 가격`도 마스터가 수정할 수 있다.
4. 장부를 수정해도 마감 상태와 최초 마감 정보는 유지한다.
5. 기존 권한, 수정 사유, 감사 로그, 충돌 방지, FIFO 재계산과 다음 날 이월 재확인 안전장치를 유지한다.

## 사용자 문제

마감 이후 다음과 같은 운영 실수가 반복적으로 발견된다.

- 다음 날 재고 이월 수량 오기입
- 당일재고 또는 표시재고 오기입
- 판매한 가격 입력 실수
- 매입·손실·지출·근무·급여·매출·결제 입력 실수

현재는 마감 상태 때문에 기존 본사 편집 기능을 그대로 사용할 수 없거나, 판매한 가격이 본사 편집 대상에 포함되지 않아 즉시 수정하기 어렵다.

운영자는 장부를 재오픈하는 복잡한 절차보다, 권한 있는 마스터가 수정 사유를 남기고 과거 장부를 바로잡는 흐름을 필요로 한다.

## 현행 기준

### 이미 존재하며 재사용할 기능

다음 항목은 기존 본사 장부 편집 화면과 저장 경로를 재사용한다.

- 매입
  - 수동 매입 행 추가·수정·삭제
  - 이카운트 행의 장부 적용 단가 보정
- 손실
  - 손실 행 추가·수정·삭제
  - 수량, 회수금액, 사유
- 재고
  - 품목 추가·삭제
  - 당일재고, 표시재고, 재고조정 사유
- 지출
  - 지출 행 추가·수정·삭제
- 근무와 급여
  - 근무인원, 업무 메모
  - 직원별 급여·지각·조퇴·특이사항
- 매출과 결제
  - 장부 마감 매출
  - 이월 매출
  - 현금·카드·기타 결제

기존 저장 경로의 다음 기능도 그대로 사용한다.

- 수정 사유 입력
- 지점 접근 범위 검사
- 감사 로그
- 낙관적 잠금에 의한 저장 충돌 방지
- 재고 조정 정합성 검사
- FIFO 재계산
- 관련 화면 재검증

### 현재 보완이 필요한 부분

- `HEADQUARTERS_CLOSED` 상태에서 기존 편집 기능이 차단된다.
- `판매한 가격`은 `StoreSalesPricePlan`에 저장되며 기존 본사 재고 저장 payload에 포함되지 않는다.
- 판매가격 수정 후 예상매출·예상마진과 손실금액 계산이 같은 날짜 기준으로 갱신되어야 한다.

## 결정 사항

### D1. 관리자 홈의 매출 구성

`매출 구성` 컬럼에는 다음 세 줄만 표시한다.

```text
매출       110,000원
예상매출    98,000원
재고금액   350,000원
```

| 표시 | 서버 값 | 규칙 |
| --- | --- | --- |
| 매출 | `row.operatingSalesAmount` | `totalSalesAmount + carryoverSalesAmount` |
| 예상매출 | `row.analysisSalesAmount` | 기존 분석 매출 계산을 유지하고 라벨만 변경 |
| 재고금액 | `row.inventoryAmount` | 선택일 장부의 서버 계산 재고 총액 |

추가 규칙:

- 관리자 홈에서 `장부 마감`, `이월`, `영업 합계`, `분석` 줄을 제거한다.
- `closingSalesAmount`, `carryoverSalesAmount` 데이터는 기존 계산·리포트 계약을 위해 유지한다.
- 재고금액은 클라이언트에서 다시 합산하지 않는다.
- 일부 품목의 계산 근거가 없으면 부분합을 정상 금액처럼 표시하지 않는다.

### D2. 재고금액 상태

| 장부 상태 | 표시 |
| --- | --- |
| `HEADQUARTERS_CLOSED` | FIFO 기준 재고 총액 |
| `IN_PROGRESS` | `마감 전` |
| `IN_REVIEW` | `마감 전` |
| `HOLIDAY` | `해당 없음` |
| 장부 없음 | `데이터 부족` |
| 계산 근거 부족 | `데이터 부족` 또는 `계산 불가` |

### D3. 실제 / 예상 마진율

다음 한 줄만 유지한다.

```text
실제 35.9% / 예상 34.4%
```

화면에서 제거:

- `경보 기준 90.0%`
- `90.0% 기준 미달 금액 ...`

업무 규칙에서 유지:

- 임계값 설정과 저장값
- 이상 신호 계산
- 확인 필요 필터
- 문제 우선순위

### D4. 마스터 계정의 정의

이메일이나 사용자 이름으로 마스터를 판별하지 않는다.

마감 장부 수정 전용 권한을 사용한다.

```text
PermissionAction.LEDGER_CLOSED_EDIT
```

기본 권한:

| 프로파일 | 마감 장부 직접 수정 |
| --- | --- |
| `OWNER` | 허용 |
| `HQ_ADMIN` | 허용 |
| `HQ_STAFF` | 불허 |
| `CLOSE_MANAGER` | 불허 |
| `HQ_READONLY` | 불허 |
| `SETTINGS_ADMIN` | 불허 |
| `STORE_MANAGER` | 불허 |

서버 조건:

1. 활성 `HEADQUARTERS` 사용자
2. 대상 지점이 사용자의 접근 범위에 포함
3. 일반 장부 수정 권한 `LEDGER_EDIT` 보유
4. 마감 장부인 경우 `LEDGER_CLOSED_EDIT` 추가 보유

### D5. 기존 편집 기능 재사용

마스터 마감 장부 수정은 별도의 새 장부 편집 시스템을 만들지 않는다.

기존 본사 편집 컴포넌트와 저장 action을 그대로 사용하고, 서버에서 마감 상태와 추가 권한만 확인한다.

- `IN_PROGRESS`, `IN_REVIEW`: 기존 정책대로 편집
- `HEADQUARTERS_CLOSED`: `LEDGER_EDIT`와 `LEDGER_CLOSED_EDIT`가 모두 있을 때 편집
- `HOLIDAY`: 계속 읽기 전용

직접 수정하지 않는 시스템 정보:

- `ledgerId`, `storeId`, `closingDate`
- `status`, `closedAt`, `closedById`
- `createdAt`, `createdById`
- 이카운트 원본 파일·원본 행·원본 단가
- 기존 감사 로그와 과거 정정 이력

### D6. 판매한 가격 수정

`판매한 가격`은 지점장이 입력한 값이더라도 마스터가 해당 날짜의 마감 장부에서 수정할 수 있다.

저장 위치:

```text
StoreSalesPricePlan.plannedUnitPrice
```

식별 키:

```text
(storeId, businessDate, productId)
```

규칙:

- 본사 마감 장부 재고 편집 화면에 `판매한 가격` 입력을 제공한다.
- 기존 재고 편집 화면과 같은 품목 행에서 수정한다.
- 저장 날짜는 장부의 `closingDate`를 사용한다.
- 다른 날짜의 판매가격은 자동 변경하지 않는다.
- 0원은 기존 숫자 입력 계약에 따라 유효한 값으로 취급한다.
- 기존 가격을 빈칸으로 바꾸는 동작은 삭제로 처리하지 않는다.
- 기존 가격이 없던 품목은 다른 재고 항목을 저장할 수 있어야 한다.
- 판매가격을 수정하면 해당 날짜의 예상매출과 예상마진을 다시 계산한다.
- 판매가격을 손실금액 계산 기준으로 사용하는 경우 해당 날짜의 손실금액도 같은 기준으로 갱신한다.
- 품목별 반복 DB 저장을 만들지 않고 기존 벌크 저장 방식을 재사용한다.

### D7. 마감 상태 유지

마스터가 업무 내용을 수정해도 장부는 계속 `HEADQUARTERS_CLOSED` 상태로 남는다.

유지할 값:

- `status`
- 최초 `closedAt`
- 최초 `closedById`

갱신할 값:

- `updatedAt`
- `updatedById`
- `version`

화면 안내:

```text
마감 상태 유지 · 마스터 수정
```

저장 성공 안내:

```text
마감 장부 내용을 저장했습니다. 마감 상태는 유지됩니다.
```

### D8. 수정 사유, 감사와 충돌 방지

기존 본사 편집 안전장치를 마감 장부에도 동일하게 적용한다.

- 수정 사유 필수
- 공백 제거 후 1~500자
- 서버에서 권한과 장부 상태 재검사
- `version` 또는 `updatedAt` 기반 충돌 방지
- 오래된 화면의 저장은 거부
- 저장과 감사 로그를 같은 DB 트랜잭션에서 처리
- 감사 로그의 `before`와 `after`는 사용자에게 실제 적용된 유효값 기준
- 감사 payload에 다음 문맥을 포함
  - `ledgerStatusAtEdit: "HEADQUARTERS_CLOSED"`
  - `closedEdit: true`

### D9. 기존 정정 이력과 직접 수정

기존 `CorrectionRecord`가 있는 장부도 마스터가 수정할 수 있어야 한다.

제품 결과 기준:

- 편집 화면은 현재 적용 중인 정정값을 반영한 값을 보여준다.
- 직접 저장 후 같은 정정이 다시 원본 위에 중복 적용되지 않는다.
- 과거 정정 기록은 삭제하지 않고 이력으로 보존한다.
- 대시보드·리포트·상세 화면은 현재 유효한 값만 사용한다.
- 직접 저장과 정정 저장이 동시에 발생하면 늦은 요청을 충돌로 차단한다.

구현은 기존 정정 모델과 조회 계약을 최대한 재사용한다. 정정 통합을 위해 상태 필드가 필요하더라도, 기존 이력을 삭제하거나 변경하는 방식은 사용하지 않는다.

### D10. 재고, FIFO와 다음 날 장부

과거 장부의 매입·손실·재고 또는 판매가격을 수정하면 해당 날짜의 관련 값을 다시 계산한다.

- 재고 조정 정합성
- FIFO lot snapshot
- 품목별 재고금액
- 장부 총 재고금액
- 매출원가
- 실제 마진율
- 예상매출과 예상 마진율
- 판매가격 기반 손실금액

다음 날 정책:

- 다음 날에 이미 입력한 실제 재고와 업무 내용은 자동으로 덮어쓰지 않는다.
- 수정된 앞 장부의 이월 수량 또는 FIFO 원가 근거가 다음 장부와 달라지면 `이월 재확인 필요`를 표시한다.
- 마스터는 영향받은 다음 장부를 열어 실제 수량을 확인하고 필요하면 직접 수정한다.
- 확인 과정과 저장에도 수정 사유와 감사 이력을 남긴다.
- 재확인 완료 처리 방식은 아래 Open questions에서 운영 기준을 확정한 뒤 구현한다.

## 제품 목표

- 관리자 홈에서 매출·예상매출·재고금액을 빠르게 비교한다.
- 반복되는 경보 기준 문구를 줄이고 실제·예상 마진에 집중한다.
- 마스터가 마감 후 발견된 운영 실수를 즉시 수정한다.
- 기존 편집 기능을 다시 만들지 않고 검증된 화면과 저장 경로를 재사용한다.
- 지점장이 잘못 입력한 판매한 가격을 해당 날짜 기준으로 바로잡는다.
- 과거 수정이 다음 날 입력을 조용히 덮어쓰지 않게 한다.

## Non-goals

- 기존 본사 편집 화면 전체 재구축
- 새로운 장부 편집 UX 별도 개발
- 모든 본사 직원에게 마감 장부 수정 권한 부여
- 휴무 장부 편집
- 장부 재오픈·재제출·재마감 절차 추가
- 미래 장부 실제 입력 자동 덮어쓰기
- 판매가격 일괄 삭제 기능
- 과거 감사 로그 삭제 또는 변경
- 이월 매출 계산 계약 변경

## 사용자 흐름

### 마감 장부 일반 항목 수정

```text
마스터 로그인
  → 과거 마감 장부 상세 열기
  → 기존 업무 탭 선택
  → 기존 편집 화면에서 값 수정
  → 수정 사유 입력
  → 저장
  → 마감 상태 유지
  → 감사 이력 확인
```

### 판매한 가격 수정

```text
마스터 로그인
  → 과거 마감 장부 상세 열기
  → 재고 탭 선택
  → 해당 품목의 판매한 가격 수정
  → 수정 사유 입력
  → 저장
  → 해당 날짜 예상매출·예상마진·관련 손실금액 갱신
  → 다른 날짜 가격은 유지
```

### 다음 날 이월 재확인

```text
과거 재고/FIFO 근거 수정
  → 다음 장부의 기존 실제 입력은 유지
  → 이월 재확인 필요 표시
  → 마스터가 다음 장부를 열어 실제 수량 확인
  → 필요하면 기존 재고 편집 기능으로 수정
  → 사유·감사 기록과 함께 재확인 완료
```

## 화면 요구사항

### 관리자 홈

- 데스크톱과 모바일 모두 `매출`, `예상매출`, `재고금액` 라벨을 동일하게 사용한다.
- 실제·예상 마진율은 한 줄을 기본으로 한다.
- 금액은 기존 원화 포맷과 tabular number 스타일을 사용한다.
- 390px 화면에서 세 지표가 겹치거나 잘리지 않아야 한다.

### 마감 장부 상세

마스터 편집 가능 상태에서 다음 안내를 표시한다.

```text
마감 상태 유지 · 마스터 수정
이 장부의 업무 내용을 수정할 수 있습니다.
저장해도 본사 마감 상태는 유지되며 수정 사유가 필요합니다.
```

재고 탭:

- 기존 재고 입력 항목 유지
- `판매한 가격` 입력 추가
- 동일 값을 읽기 전용 텍스트와 입력창으로 중복 표시하지 않는다.
- 저장 오류는 해당 가격 입력으로 포커스를 이동한다.

권한 없는 사용자와 `HOLIDAY` 장부는 기존 읽기 전용 화면을 유지한다.

## 접근성

- 기존 키보드 탭 이동과 저장 버튼 동작을 유지한다.
- 저장 오류는 첫 오류 필드로 포커스를 이동한다.
- 마감 상태 유지와 수정 사유 필수 안내는 색상만으로 전달하지 않는다.
- 충돌 안내 dialog는 스크린 리더가 읽을 수 있어야 한다.
- 모바일 `<dt>/<dd>` 라벨은 데스크톱 의미와 일치시킨다.

## 구현 원칙

1. 기존 본사 편집 컴포넌트와 action을 재사용한다.
2. 마감 수정 권한은 서버가 최종 판정한다.
3. client prop은 입력 표시만 제어하며 기본값은 `false`다.
4. 상태·최초 마감 정보는 변경하지 않는다.
5. 판매가격은 기존 `(storeId, businessDate, productId)` 저장 계약을 재사용한다.
6. 계산은 서버에서 수행하고 UI는 결과만 표시한다.
7. 과거 수정은 다음 날 실제 입력을 자동 변경하지 않는다.
8. 기존 정정·감사 이력을 삭제하지 않는다.
9. 저장과 관련 계산·감사 갱신은 가능한 한 같은 트랜잭션 경계를 유지한다.
10. 대시보드에 행별 추가 DB 조회를 만들지 않는다.

## 수용 기준

### 관리자 홈

- [ ] `매출 구성`에 `매출`, `예상매출`, `재고금액`만 표시한다.
- [ ] 별도 `이월`, `장부 마감`, `영업 합계`, `분석` 줄이 없다.
- [ ] 매출은 기존 합산 매출과 같다.
- [ ] 예상매출 계산식은 기존 분석 매출과 같다.
- [ ] 마감 장부 재고금액은 FIFO 기준 총액과 같다.
- [ ] 미마감 장부는 `마감 전`, 휴무는 `해당 없음`, 장부 없음은 `데이터 부족`으로 표시한다.
- [ ] 일부 품목의 계산 근거가 없으면 부분합을 정상 금액으로 표시하지 않는다.

- [ ] 390px 화면에서 세 지표와 마진이 겹치거나 잘리지 않는다.

### 마감 장부 수정

- [ ] 기존 본사 편집 화면과 저장 action을 재사용한다.
- [ ] OWNER/HQ_ADMIN만 마감 장부 원본을 직접 수정할 수 있다.
- [ ] HQ_STAFF, CLOSE_MANAGER, HQ_READONLY, STORE_MANAGER는 수정할 수 없다.
- [ ] `HOLIDAY` 장부는 계속 읽기 전용이다.
- [ ] 매입·손실·재고·지출·근무·급여·매출/결제를 기존 기능과 동일하게 수정할 수 있다.
- [ ] 지점장이 입력한 해당 날짜의 `판매한 가격`을 재고 탭에서 수정할 수 있다.

- [ ] 오래된 화면 저장은 충돌로 거부된다.

- [ ] 과거 재고/FIFO 수정 후 다음 날 실제 입력은 자동 변경되지 않는다.
- [ ] 영향받은 다음 장부에는 `이월 재확인 필요`가 표시된다.

## 배포 및 호환

1. 권한 action을 추가하는 경우 enum migration과 프로파일 권한 부여를 안전한 순서로 배포한다.
2. 기존 OWNER/HQ_ADMIN에만 새 권한을 부여한다.
3. HQ_STAFF에는 자동 부여하지 않는다.
4. 기존 본사 편집 기능과 진행 중·검토 대기 장부 동작을 회귀 검증한다.
5. 기존 판매가격과 장부 데이터는 일괄 변경하지 않는다.
6. 기존 감사 로그와 정정 기록을 일괄 수정하거나 삭제하지 않는다.
7. 대표 마감 장부에서 기존 항목 수정과 판매가격 수정 흐름을 smoke test한다.
